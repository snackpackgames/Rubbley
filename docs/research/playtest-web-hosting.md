# Hosting the `main` playtest web build

Research for [#87](https://github.com/snackpackgames/Rubbley/issues/87). Gathered 2026-10-21.

Context: CI publishes a web export of every merge to `main` to a stable playtest location ([ADR 0011](../adr/0011-gdunit4-split-suites-linux-ci.md)). That build is always the Full Game and never ships ([ADR 0015](../adr/0015-storefronts-unlock-platform-services.md)). Rubbley is GDScript-only on Godot 4.7 (latest stable [4.7.2](https://github.com/godotengine/godot/releases/tag/4.7.2-stable)) with the Compatibility renderer ([ADR 0010](../adr/0010-compatibility-renderer-performance-floors.md)). `snackpackgames/Rubbley` is a public repo, and the `snackpackgames` org is on GitHub Free (GitHub API, 2026-10-21).

## Summary

| Host | COOP/COEP headers | Fits stock 4.7.2 template? | Access control | Deploy from Actions | Old builds / PR previews | Cost |
|---|---|---|---|---|---|---|
| GitHub Pages | No custom headers | Yes: 1 GB site limit, no per-file limit | Public only on GitHub Free. Private Pages needs Enterprise Cloud | `upload-pages-artifact` + `deploy-pages` | One live site. No native previews | Free (public repo) |
| itch.io | Yes, through the "SharedArrayBuffer support" checkbox | Yes: 200 MB per file, 500 MB total | Draft, Restricted (password or download key, hidden from search), Public | butler with `BUTLER_API_KEY` | One build per channel is live. Each channel is a separate upload | Free |
| Cloudflare Pages / Workers static assets | Yes, `_headers` file | **No**: 25 MiB per-file cap, and `godot.wasm` is 37.7 MiB | Previews behind Access with one toggle. Production needs Cloudflare Access with a domain on Cloudflare | `wrangler` | Unlimited previews at `<hash>.<project>.pages.dev` and branch aliases | Free tier |
| Netlify | Yes, `_headers` or `netlify.toml` | Probably: no documented per-file cap, untested at 37.7 MiB | Password protection only on Pro ($20/month) | Netlify CLI | Unlimited deploy previews, free of credits | Free: 300 credits/month, 15 per production deploy, 20 per GB of bandwidth. Sites pause at 0 |

The single-threaded export (the default) needs none of the headers, so header support only matters if the project turns threads on.

## Godot 4.7 web export requirements

### Threads and cross-origin isolation

- **Single-threaded is the default.** In the 4.7.2 source, `variant/thread_support` defaults to `false`, with the comment "Thread support (i.e. run with or without COEP/COOP headers)" ([export_plugin.cpp L375](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/web/export/export_plugin.cpp#L375)). The docs call single-threaded "the preferred and now default way to export your games on the Web", available since 4.3 ([Exporting for the Web](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)).
- **Threads need cross-origin isolation.** A threaded export uses `SharedArrayBuffer` and needs a secure context plus `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`. Without them "the project will not run". Isolation means "no ads, nor third-party integrations on the website hosting your game" ([Exporting for the Web](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)).
- **The PWA workaround.** With `progressive_web_app/enabled`, the option `progressive_web_app/ensure_cross_origin_isolation_headers` (default `true`, [export_plugin.cpp L386](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/web/export/export_plugin.cpp#L386)) installs a service worker that simulates the headers, so a threaded build can run on a host that can't send them. It still needs HTTPS. Its cost is service-worker caching, which "currently lacks an automated cache busting mechanism", so playtesters can get a stale build after a redeploy ([Exporting for the Web](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)). For a build that changes on every merge, that matters.
- **What single-threaded costs.** It "cannot use threads, and is not as performant as the multi-threaded export". Audio defaults to Sample playback, which gives low latency without threads but doesn't support AudioEffects, reverb, doppler or procedural audio, and positional audio "may not always work correctly". Switching to Stream playback restores those features at the price of more latency, "especially when thread support is disabled" ([Exporting for the Web](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)).

### Renderer and mobile browsers

- "Godot 4 can only target WebGL 2.0 (using the Compatibility rendering method)" ([Exporting for the Web](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)). That matches ADR 0010.
- **iOS Safari:** "Safari has several issues with WebGL 2.0 support that other browsers don't have", and the docs recommend Chromium or Firefox. Every iOS browser uses Safari's engine, so phones on iOS get those issues whatever browser they use. On the other hand, "the single-threaded export works very well on macOS and iOS too, where it always had compatibility issues with multiple threads exports" ([Exporting for the Web](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)).
- **Android Chrome:** the docs give no Android-specific caveats, only that "CPU and GPU performance is at a premium when running on mobile devices" and native exports "will always perform better by a significant margin".
- **Texture compression:** `vram_texture_compression/for_mobile` (ETC2/ASTC) defaults to `false` and `for_desktop` (S3TC/BPTC) to `true` ([export_plugin.cpp L376-377](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/web/export/export_plugin.cpp#L376-L377), [EditorExportPlatformWeb](https://docs.godotengine.org/en/4.7/classes/class_editorexportplatformweb.html)). Phone playtests probably want the mobile set enabled. Not verified on devices here.

### Size and serving

- Measured from the official 4.7.2 export templates (range-read from [`Godot_v4.7.2-stable_export_templates.tpz`](https://github.com/godotengine/godot/releases/tag/4.7.2-stable)): `web_nothreads_release.zip` holds a **`godot.wasm` of 39,514,754 bytes (37.7 MiB)**. The threaded `web_release.zip` holds 38,820,072 bytes (37.0 MiB). The other files (`godot.js`, worklets, service worker, HTML) are under 0.3 MiB. The game's `.pck` comes on top.
- Serve `.wasm` as `application/wasm` and `.pck` as `application/octet-stream`. Compressing the `.wasm` brings it to "around a quarter of its original size with gzip". GitHub Pages gzips on the fly. itch.io and GitLab Pages don't ([Exporting for the Web](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)), although itch.io's CDN gzips `.pck` and some other extensions you upload uncompressed ([itch.io HTML5 docs](https://itch.io/docs/creators/html5)).

### Local saves (ADR 0015)

- `user://` maps to `/userfs/<user dir>` in an IndexedDB-backed filesystem ([os_web.cpp L210-213](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/web/os_web.cpp#L210-L213)). IndexedDB is scoped per origin (scheme + host + port), not per path. So saves survive a redeploy whenever the URL's origin and the project's user dir name stay the same.
- Persistence fails if the user blocks cookies/IndexedDB, uses private browsing, or (in an iframe) blocks third-party cookies. Browsers may also evict the data under disk pressure or "if the user hasn't opened the project for a while". `OS.is_userfs_persistent()` "can give false positives" ([Exporting for the Web](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_for_web.html)). Embedding hosts like itch.io run the game in an iframe on a CDN origin, so the third-party cookie rule applies there.

## GitHub Pages

- **Limits:** a published site is at most 1 GB, a deployment times out after 10 minutes, and bandwidth has a soft limit of 100 GB/month. The 10-builds-per-hour soft limit "does not apply if you build and publish your site with a custom GitHub Actions workflow". No per-file limit is listed ([Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)).
- **Deploying:** `actions/upload-pages-artifact` packages a gzip tar under 10 GB, and `actions/deploy-pages` deploys it ([custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)). Each deployment replaces the live site, so keeping old builds means CI copies them into subfolders of the next artifact, or deploys from a branch instead.
- **Headers:** the limits page doesn't mention custom headers, and Pages has no way to set them. A threaded build would need the PWA service-worker workaround. The single-threaded default needs nothing.
- **Access control:** on GitHub Free the repo must be public, and the site is public ([creating a Pages site](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)). Private sites, readable only by people with read access to the repo, need GitHub Enterprise Cloud ([Pages visibility](https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site)). The URL would be `snackpackgames.github.io/Rubbley/`, findable but not linked from anywhere unless we link it.
- **PR previews:** none native. ADR 0011 already uploads each PR's web export as a workflow artifact.
- **Saves:** every project site in the org shares the `snackpackgames.github.io` origin, so saves survive redeploys and are separated from other games only by Godot's user dir name.

## itch.io

- **Visibility:** Draft is "only available to project owners", Restricted is "available to people you've permitted" by download key or by a password on the page, and Public is open. "Restricted projects will not show up on itch.io's browse pages, search results, or profile pages", nor in external search engines ([access control](https://itch.io/docs/creators/access-control)). A playtest page would be a separate project, set to Restricted with a password, next to the public Free Tier page.
- **Limits:** at most 1,000 files, 500 MB extracted, 200 MB for any single file, 240-character paths ([HTML5 docs](https://itch.io/docs/creators/html5)). The 37.7 MiB `godot.wasm` fits.
- **Mobile:** the "Mobile Friendly" embed option makes phones use "Click to launch in fullscreen". Without it, phones see a warning that the game may not work ([HTML5 docs](https://itch.io/docs/creators/html5)).
- **SharedArrayBuffer:** the checkbox is under Embed Options > Frame Options. It serves the game from `html.itch.zone` with `Cross-Origin-Opener-Policy: same-origin` on HTML files and `Cross-Origin-Embedder-Policy: require-corp` plus `Cross-Origin-Resource-Policy: cross-origin` on all files. Third-party iframes on the page (such as YouTube in comments) stop working, and Safari still needs the game opened in a separate window. Switching it on moves the game to a new domain, so existing local-storage saves become unreachable (staff announcement, [itch.io forum, 2022-04-02 with later updates](https://itch.io/t/2025776/experimental-sharedarraybuffer-support)). This is a forum post, not the creator docs, which don't mention the option. Only a threaded build needs it.
- **CI:** butler pushes to a channel. A new channel creates a new upload, and pushing again updates it. Marking an upload as playable in the browser, and setting the page type to HTML, is a manual one-time step on the Edit page after the first push. `--userversion` sets a version label ([butler pushing](https://itch.io/docs/butler/pushing)). Running butler from Actions needs only `BUTLER_API_KEY` on any runner ([storefront research](https://github.com/snackpackgames/Rubbley/blob/research/godot-storefront-integrations/docs/research/godot-storefront-integrations.md)).
- **Old builds:** a channel holds one live build. The docs don't say whether older builds can be restored. Keeping several builds playable would mean several channels or pages.
- **Saves, and the clash with the Free Tier:** classic HTML games are served from the shared origin `html-classic.itch.zone`, with each game at `/html/<id>/index.html` (seen on a live itch.io page on 2026-10-21). Because IndexedDB is per origin, saves survive redeploys. But **the Free Tier page and a playtest page would share the same IndexedDB, and with the same Godot project name they'd read and write the same `user://` files** in a tester's browser. A distinct user dir for the playtest build would avoid that. (This follows from the origin and `os_web.cpp` facts above. It wasn't tested.)

## Cloudflare Pages and Workers static assets

- **Blocker:** "The maximum file size for a single Cloudflare Pages site asset is 25 MiB." The Free plan allows 20,000 files per site, 500 builds a month, and unlimited active preview deployments ([Pages limits](https://developers.cloudflare.com/pages/platform/limits/)). Workers static assets have the same 25 MiB per-file cap, with 20,000 files on Free and 100,000 on Paid ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). The stock 4.7.2 `godot.wasm` is 37.7 MiB, so a stock export can't be deployed. It would need a custom export template built for size, which is a C++ build step in CI rather than GDScript.
- **Headers:** a `_headers` file can add or override response headers, with up to 100 rules ([Pages headers](https://developers.cloudflare.com/pages/configuration/headers/)).
- **Previews:** each deployment gets `<hash>.<project>.pages.dev`, and each branch gets an alias. "Enable access policy" restricts previews to the Cloudflare account, but "will only protect your preview deployments", not production. Protecting production needs Cloudflare Access ([preview deployments](https://developers.cloudflare.com/pages/configuration/preview-deployments/)), and a self-hosted Access application needs "an active domain on Cloudflare" ([Access self-hosted apps](https://developers.cloudflare.com/cloudflare-one/applications/configure-apps/self-hosted-public-app/)). The free Access seat count wasn't confirmed from a primary source.
- **Saves:** each preview hash is its own origin, so saves don't carry between previews. The production URL keeps its origin across deploys.

## Netlify

- **Headers:** set in `_headers` in the publish directory or `[[headers]]` in `netlify.toml`. They are "global for all builds and cannot be scoped for specific branches or deploy contexts" without a copy-at-build workaround ([Netlify headers](https://docs.netlify.com/manage/routing/headers/)).
- **Access control:** "Password protection isn't available on Credit-based Free and Personal plans". It is available on Pro ([password protection](https://docs.netlify.com/manage/security/secure-access-to-sites/password-protection/)), which costs $20/month. Personal is $9/month ([pricing](https://www.netlify.com/pricing/)).
- **Cost model:** Free gets 300 credits. "Each successful production deploy consumes 15 credits", deploy previews and branch deploys cost nothing, and bandwidth costs 20 credits per GB. At 0 credits on Free "all of your web projects (sites/apps) are paused" and visitors see `Site not available`, with no option to buy more ([how credits work](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/)). A production deploy on every merge to `main` would use the Free allowance after 20 merges a month, before counting bandwidth. A playtester downloading the uncompressed ~40 MB engine once costs about 0.8 credits.
- **File size:** the docs give no per-file cap. The only stated limit is 54,000 files per directory ([deploy overview](https://docs.netlify.com/deploy/deploy-overview/)). A Netlify support-forum answer recommends files of no more than 10 MB per deploy ([forum](https://answers.netlify.com/t/what-is-the-maximum-allowed-object-size/145182)). That is not documented, and a 37.7 MiB file wasn't tested.
- **Saves:** deploy previews have their own subdomains, so they are separate origins. The production URL keeps its origin.

## Not covered

Whether a restricted itch.io page can host a playable HTML5 upload behind its password wasn't confirmed in the docs. The access-control page doesn't mention HTML5.
